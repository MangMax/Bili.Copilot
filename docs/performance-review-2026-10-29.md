# Bili Copilot 性能审查报告

审查日期：2026-10-29  
代码基线：`4344ae756344f3ed6f1c11bd3216320b9143996f`  
方法：全局模式检索、关键调用链静态审查、XAML 与生命周期交叉核对。未修改应用代码。

## 结论与边界

存在明确的性能优化空间，优先处理 AI 流式渲染、弹幕加载生命周期、Markdown 强制 GC 和首页加载依赖。以下列出 11 项代码中可确认的开销或设计风险，以及需要性能采样才能定性的候选项。P1 表示优先安排，P2 表示后续优化，P3 表示低优先级整理；不是已测得的卡顿严重度。

这是源码性能审查，不是已经完成的整机性能测试。此次没有启动应用、构建、运行测试、运行 WinUI 分析器或采集 ETW/CPU/GPU/内存快照；没有实测启动耗时、帧率、内存占用或优化收益百分比。第三方 NuGet 库与原生 mpv、弹幕引擎内部没有完整审计。不得将报告理解为“所有性能问题均已找到”或“已证实内存泄漏”。

覆盖：应用启动与 DI、首页和分页、搜索联想、页面缓存、图片与 Markdown、AI 流式输出、播放器与弹幕、下载进程、通知定时器、SponsorBlock 缓存、Visor 管道以及直接项目引用的 bili-kernel HTTP 层。评论、动态、收藏、历史等界面进行了结构与模式扫描，未逐条验证全部业务分支。

下文位置以仓库根目录为起点，行号对应本次基线；`UI/` 简写为 `src/Desktop/BiliCopilot.UI/`，`Kernel/` 简写为 `externals/bili-kernel/src/BiliKernel.Core/`。

## 一、优先处理

### F01 · P1 · AI 流式输出反复全量解析与重建 Markdown

**证据**：`UI/ViewModels/Core/AIViewModel/AIViewModel.Chat.cs:388,418–427`；`UI/Controls/AI/AIBody.xaml` 的 `TempResult` 绑定；`UI/Controls/Markdown/MarkdownTextBlock.xaml.cs:99–107`；`UI/Controls/Markdown/Renderers/WinUIRenderer.cs:40–51`。

每个响应分片分别拼接 `responseContent`，并向 UI 队列提交 `TempResult += text`。文本属性改变会解析当前全部 Markdown，清空旧文档和渲染器集合，再重新创建内容。长回复、代码块、表格或图片会放大字符串复制、对象分配和 UI 布局开销。固定大小分片下，累计字符串复制及全量解析的输入规模近似二次增长；实际耗时尚未测量。

**建议**：后台用 StringBuilder 累积文本；按可调时间窗口合并 UI 更新，例如先试 50–100ms；生成期间显示纯文本或仅重建末尾未完成块，结束后完整渲染一次。解析可以移到后台，XAML 元素创建仍留在 UI 线程。队列回调绑定生成会话版本，取消后立即返回，避免旧回调继续追加文本。

**验收**：用确定性的流式分片重放相同长回复，记录 UI 更新次数、分配量、GC 暂停和输入响应；校验最终文本完整、取消后无追加、Markdown 格式正确。不能只更换 StringBuilder 而保留逐分片全量 UI 重建。

### F02 · P1 · Markdown 清理直接触发全堆 GC

**证据**：`UI/Controls/Markdown/MarkdownTextBlock.xaml.cs:110–120`。

控件卸载或文本清空时调用 `Clean()`，其中执行无参数 `GC.Collect()`。局部控件清理因此影响整个进程托管堆；应用中的其他页面、播放器控制对象也受到垃圾回收调度影响。该调用不是每个流式分片都触发，不能和 F01 混为一谈。

**建议**：移除常规交互路径上的强制 GC，正常解除引用、取消异步工作并释放原生资源。若历史上为规避泄漏而加入，先通过存活对象引用链找出真实持有者。

**验收**：反复生成、清空和关闭 AI 面板，比较交互路径上的 GC 事件与暂停；验证对象在自然 GC 后可回收，避免用“任务管理器内存立即下降”作为唯一标准。

### F03 · P1 · 弹幕全量预取且未随切片/关闭取消

**证据**：`UI/ViewModels/Core/PlayerViewModel/PlayerViewModel.Danmaku.cs:27–84`；同目录 `PlayerViewModel.cs:26–90`。

按六分钟分段，为整段视频创建任务，最多六个请求并发；等待全部任务结束后才执行 `Danmaku.Initialize(danmakus)`。请求和信号量等待没有播放会话取消令牌。关闭播放器虽然清空了弹幕，但这里正在执行的任务仍可能继续请求、持有数据，并在完成后再次写入弹幕状态。切换视频也缺少该加载结果所属会话的校验。

影响是首批弹幕展示等待、长视频不必要的网络/内存开销以及过期结果回写风险；**不能据此断言视频首帧也等待所有弹幕**。现有六并发限制是有效保护，并非无限并发。

**建议**：按播放会话建立 CTS，切换和关闭时取消；请求、限流等待和结果发布均检查令牌/会话版本。优先加载当前位置与邻近分段，后台按需预取，设置缓存预算；处理 seek、重试、分段排序和去重。纯异步网络任务不必每段再包 Task.Run；信号量使用确定性释放。

**验收**：长视频加载中连续切换分 P 并关闭窗口；确认旧会话不再提交数据，等待中的分片不继续启动；首段可先于远端慢分片显示，拖动后目标附近弹幕正常。

### F04 · P1 · 首页内容被无关分区请求和固定延迟串行阻塞

**证据**：`UI/ViewModels/View/PopularPageViewModel/PopularPageViewModel.cs:36–67`。

首次初始化先 `await LoadPartitionsAsync()`，再 `await Task.Delay(200)`，最后选择栏目并加载视频。默认推荐/热门并不依赖完整分区列表，也会被分区接口拖慢。200ms 是路径中明确存在的主动等待，不是本次测出的整体启动耗时。

**建议**：先恢复推荐/热门栏目并加载内容，分区侧栏独立获取；仅在恢复特定分区排行时等待分区信息。用真实控件就绪信号替代固定延迟，并检查它原本是否用于规避布局重入。

**验收**：故意延迟或失败分区接口，推荐内容仍能独立出现；上次选择分区排行的恢复行为保持正确。分别记录窗口可见、推荐首批数据、卡片可交互时间。

## 二、后续优化

### F05 · P2 · 弹幕重绘条件使单渲染器模式始终额外等待

**证据**：`UI/Controls/Danmaku/VideoDanmakuPanel.xaml.cs:40–50,256–290`。

Win2D 与 DirectX 正常情况下只启用其中一个，但 `Redraw()` 使用 `_danmakuRenderer == null || _danmakuMaster == null` 判断是否延迟。因此正常单引擎状态也进入 500ms 延迟。连续重绘没有合并，随后在低优先级 UI 回调中转换整份弹幕。

**建议**：按当前选定引擎检查就绪状态；至少修正“两个都不存在”与“任一个不存在”的语义差异。合并重绘请求，对不可变弹幕转换结果做会话级复用；判断解析器线程安全后再考虑后台转换。

**验收**：两种引擎各自测试启用、切换、快进和连续重绘，无不必要等待、旧任务覆盖或重复初始化。空条件调用会短路，当前代码不能据两行调用就认定每次解析了两遍。

### F06 · P2 · 首页数据缓存与页面保留没有明确内存预算

**证据**：`UI/GlobalDependencies.cs:104`；`UI/Controls/MainFrame.xaml.cs:91,103`；`UI/ViewModels/View/PopularPageViewModel/PopularPageViewModel.cs:82–108`；同目录 `PopularPageViewModel.Requests.cs` 的 `TryAddVideos()`。

主框架保留已创建页面，只切换可见性；热门页 ViewModel 为单例。推荐/热门数据不断追加，切换栏目时把完整列表放入 `_videoCache`，未见该缓存容量或时间上限。回到栏目时清空 ObservableCollection 并逐条加回全部缓存对象，也会产生与列表长度相关的通知与绑定开销。

这是明确的保留策略和增长风险，**不等同于泄漏**。页面类型数量有限，不能称“导航次数导致页面对象无限增加”；列表内容本身才是主要增长维度。

**建议**：为每栏目、总缓存分别设条目/内存预算和淘汰策略，保存轻量滚动锚点；限制长时间浏览的驻留数据。批量更新策略须与实际控件兼容，不能盲目使用 Reset 导致整个可视列表重建。

**验收**：持续翻页、切换栏目后，数据量在预算内稳定；返回位置可恢复；分别观察托管对象、图像原生资源与总私有内存，避免只看工作集。

### F07 · P2 · 搜索联想缺少输入防抖，正常取消也记录错误

**证据**：`UI/Controls/Components/AppSearchBox.xaml.cs:39–70`；`UI/ViewModels/Components/SearchBoxViewModel/SearchBoxViewModel.cs:37,90–108`。

用户输入变化即执行联想命令；方法会取消旧请求，但没有等待用户输入短暂停顿。取消不能保证请求尚未发往服务器。通用异常捕获还把正常取消作为错误记录。控件已有 600ms 提交抑制窗口，但用于选择联想项后的输入法事件，不是普通输入防抖。

**建议**：输入防抖可从 200–300ms 试起，保留即时取消；只提交最新关键字版本结果；将正常 OperationCanceledException 与网络错误分开。保持已有输入法、焦点和区域搜索行为。

**验收**：录制快速输入、输入法组合和删除过程，统计实际发出的请求、错误日志与联想展示延迟；旧关键词结果不得覆盖新结果。

### F08 · P2 · Markdown 图片使用独立 HTTP 客户端与全尺寸解码

**证据**：`UI/Controls/Markdown/TextElements/MyImage.cs:100–140`；`UI/Controls/Markdown/MarkdownConfig.cs` 的默认配置。

默认图片路径每张图创建 HttpClient，未确定性释放客户端和 response；将响应读为字节数组，再复制到内存流，创建未指定 DecodePixelWidth/Height 的 BitmapImage。显示尺寸在后面设置，不能据此认为已限制实际解码尺寸。Markdown 重建还可能反复进入图片加载路径。

**建议**：使用专门的长寿命图片客户端或共享处理器，保持域名、Cookie 和认证边界；释放响应/流，限制下载大小与并发，按展示尺寸与 DPI 解码，使用 URI 与目标尺寸缓存，并在控件失效时取消。减少缓冲复制须兼顾 WinRT 解码所需流能力。

**验收**：固定的大图 Markdown 重复打开、缩放和关闭，观察连接创建、下载次数、分配峰值与解码内存。这里是资源释放不及时风险，尚不能断言已发生端口耗尽。

### F09 · P2 · HTTP 验证与业务解析重复处理响应

**证据**：`Kernel/Http/BiliHttpClient.Extension.cs:37–52`；`Kernel/Http/BiliHttpClient.cs:70–74,112–129`。这些源码通过项目引用进入应用，不只是未使用的外部样例。

JSON 响应先读成文本并反序列化 BiliResponse 验证，再在 ParseAsync 中读文本并反序列化目标模型；gRPC 验证读取字节，业务解析再次读取，并通过 `[.. bytes.Skip(5)]` 创建去掉头部的新数组。HTTP 内容已缓冲，**这不意味着重复下载**，但存在重复解析或复制开销。

**建议**：使错误码验证与模型解析共享一次读取/解析；对协议缓冲采用偏移读取思路，具体可用重载需按已还原依赖确认。明确 request/response 的所有权，补齐 GetStringAsync 内部响应的释放，并保持取消语义和错误信息。

**验收**：对保存的脱敏大响应离线重放，比较分配量与 CPU，确认错误码、空响应和 gRPC 头处理一致；微基准收益不能直接推导到整机启动。

## 三、低优先级整理

### F10 · P3 · 后台任务使用同步等待

**证据**：`UI/Forms/PlayerWindow.cs:188,203,224,239`；`UI/ViewModels/Core/DownloadViewModel/DownloadViewModel.cs:215–225`。

窗口切换在 Task.Run 中执行 `Task.Delay(500).Wait()`；下载进程在后台任务中 `WaitForExit()`，可能占用线程直至下载结束。两者不是直接堵塞 UI 线程，也不能在没有采样时断言已经线程池饥饿。

**建议**：使用真正异步等待；窗口状态在正确线程更新，并用版本或取消机制阻止快速切换时旧延迟清除新状态。下载等待后释放 Process，对同时下载数量作产品层约束。

**验收**：反复切换窗口模式和多下载任务并存时，等待线程不随任务长期累积；退出、下载完成打开目录的行为不变。

### F11 · P3 · 滚动加载检查逐事件入队，没有合并

**证据**：`UI/Controls/IncrementVerticalScrollControl.xaml.cs:66–87`。

每次 ViewChanged/SizeChanged 都入队一个低优先级检查，回调执行时再判断距离底部是否小于 800。快速滚动时可以重复排队相同检查。热门页有 IsVideoLoading 防重入，所以不能据此声称网络请求一定重复。

**建议**：用“已有待执行检查”标志合并队列项；执行时验证控件仍加载、命令可执行、未在加载且还有下一页。保留短列表自动补足视口的能力。

**验收**：快速滚动和窗口缩放时，队列中的待执行检查最多一份，仍能可靠触底加载，卸载后不再触发。

## 四、需要实测后决定的候选项

1. **图片后台解码**：`UI/App.xaml.cs:67` 明确关闭 `ImageExBase.EnableBackgroundDecoding`。这是重点调查点，但封面基类来自第三方库，仅凭属性名无法证明全部解码都发生在 UI 线程。先读取对应版本实现或采样，再做安全的开关对照；不能直接切为 true，因为 `BasicCoverImage` 还共享静态 `_scaleEffect`，需要检查并发访问。
2. **列表虚拟化**：主列表使用 AppRepeater、UniformGridLayout 和 ScrollView。未确认虚拟化失效。检查真实可视树中已创建卡片数是否受视口约束，以及离屏图像是否释放。不要把 ItemsRepeater 的 StackLayout 和非虚拟化 StackPanel 混为一谈。
3. **GPU、解码与视频缓存**：内置 mpv 配置已有 `hwdec=auto`、`vo=gpu-next`。`PlayerViewModel.Methods.cs:173–177` 默认设置 300MiB 解复用缓存上限与 360 秒预读；这不是启动即分配 300MiB 的证据。需要分别测硬解是否实际生效、4K/高帧率、多窗口、不同着色器和电池供电，不能笼统建议“开启硬解”或把缓存越小当成越好。
4. **播放器位置更新**：`PlayerViewModel.Methods.cs:512–529` 每次位置事件格式化字符串、广播、检查跳过片段并遍历章节。先测实际事件频率与章节数量，再决定按秒更新文本、用当前位置索引替代全遍历。未证实这里是热点。
5. **启动初始化**：DI 注册很多 AI 提供商，但注册不等于实例化全部模型。`AppViewModel` 在窗口激活后异步初始化外部路径和字体；不能把它全算入窗口首次显示的阻塞时间。需逐阶段标记启动路径。
6. **日志与磁盘缓存**：`GlobalDependencies.cs:206` 使用文件 sink，配置中未见显式异步包装及跨日期文件清理。需先测日志写入频率、文件增长和图像缓存所属第三方实现，不能直接断言磁盘缓存无限增长。优化取消日志通常比无条件异步化所有日志更直接。
7. **下载与 Visor 子进程**：下载由 BBDown/ffmpeg 执行，应把子进程 CPU、内存、磁盘计入用户感知资源开销；Visor Stop 最多同步等待五秒，应核实退出路径实际耗时。低频关闭逻辑不是目前优先热点。

## 五、已具备的保护与排除的误报

- 主封面客户端为静态共享，不能把 Markdown 图片的问题推广成“全应用每次请求都新建 HttpClient”。bili-kernel 也注册了单例客户端。
- 弹幕有六并发限制；不足在于预取范围与生命周期。
- SponsorBlock 服务有请求超时、取消、响应释放；缓存容量 200、TTL 五分钟。关闭播放器会取消它的加载。它与缺少取消的弹幕加载应分别评价。
- PlayerViewModel.DisposeAsync 已解除多处事件并释放播放器、客户端和窗口，不能笼统称“播放器无释放”。仍需快照验证第三方原生资源是否回收。
- 页面已有 x:Bind，部分内容已有 x:Load；不存在把全项目机械替换绑定方式就一定变快的依据。
- 项目已设置 PublishAot，不能将“打开 AOT”当作新增优化；发布配置中的大量裁剪警告抑制需要独立质量核查，但本报告不将它直接列为运行性能瓶颈。

## 六、性能验证方案与实施顺序

建议先建立 Release 实际发布包的基线；AOT 发布包与 Debug 运行结果分开记录。记录 OS、CPU、GPU/驱动、RAM、分辨率/DPI、显示器刷新率、电源模式、版本、账号数据规模和网络条件。固定测试素材与配置，区分冷缓存和热缓存。

**场景与指标**：

- 冷/热启动：进程开始→窗口可见→首页可交互，独立记录网络等待。
- 长列表：持续翻页并快速滚动，记录 UI 帧耗时、输入延迟、活跃卡片数、私有内存、托管堆与图像资源。
- AI：固定分片流、长文本、代码块和图片，记录每秒 UI 更新数、分配速率、GC 暂停，包含取消与关闭面板。
- 弹幕：长视频、高密度、慢分片、seek、快速换 P 与关闭，记录第一批显示时间、请求数、过期请求和会话数据存活。
- 播放：普通视频与高负载视频分别测，记录实际硬解状态、掉帧、CPU/GPU、缓存与音画同步；每次只改变一个设置。
- 生命周期：反复打开/关闭播放器及图库、浏览各页面后静置，对比托管引用链和原生/显存。长期稳定性按较长会话测试，不能仅凭一次回落判断无泄漏。
- 搜索和下载：统计真实请求次数与取消日志；下载覆盖子进程，分离网络限速与本地 CPU/磁盘瓶颈。
