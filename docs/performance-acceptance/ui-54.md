### 迟到 GotFocus 的最小诊断（保留 red）

初版没有任何 GotFocus，因 Grid 不可聚焦，零迟到事件缺少正向对照，不能充当焦点验收。于是仅修改 fixture 为 `UserControl { IsTabStop=true }` 并在 RapidFinalNormal 断言活窗口 GotFocus。此轮 71 个 live focus、9 个 late focus，18 个用例中 8 个失败。没有盲目重试。

最终诊断源码增加 GettingFocus/GotFocus 调用栈和 close 前后标记，未改生产方法或失败断言。三次最小过程均为：真实 Create/Show → ResetFocus 入队 → DelayUpdateTitleBarPadding 入队 → 同一 UI turn Close/Dispose → 1800ms 观测及低优先级队列 barrier。第一次记录：

- 16989.3982ms：GettingFocus，closed=false/disposed=false；栈包含 `PInvoke.SetFocus → PlayerWindow.Show → fixture Create`。
- 17057.5254ms：close-call；17115.6452ms：Destroying，closed=true；17126.5331ms：close-return。
- 17137.5913ms：GotFocus，closed=true/disposed=true，`IsWindow(captured HWND)=false`；栈为 WinRT routed-event → Application.Start 消息循环，**没有 PlayerWindow.ResetFocus/SetFocus 调用栈**。
- 18944.1487ms：观测结束，lateFocus=1、AfterDestroyCalls=0、IsChanging=false。

另外两轮同样有关闭前 Show/SetFocus 的 GettingFocus、关闭后消息循环派发的 GotFocus。诊断前三个窗口没有关闭后 GettingFocus，也没有关闭后 activation action/header 调用；原生 HWND 已销毁。9 次 first-chance 记录是 3 个 fixture ASSERT 在 async 传播过程重复报告；没有非断言异常或 unhandled。

**已定位的验收 oracle 问题**：`lateFocus == 0` 把“之前发生的焦点请求之迟到通知”当作“关闭后再次访问窗口”。这些日志支持前者，不能证明生产 guard 漏掉了原生访问；也不提供完整原生调用跟踪，不能反推绝对无访问。没有确认必须修改生产的 #54 回归。保留 [复验 red](evidence-54-focus/results.json) 和 [三轮最小 red](evidence-54-diagnostic/results.json)，不将它们改写为绿色。完整焦点生命周期验收仍有缺口。
