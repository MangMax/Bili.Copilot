## 关闭窗口 ≠ 应用退出

keeper 是显式的 **harness-only** 生命周期正对照，不是生产 MainWindow。第一次关闭 owned main 后进程还活着，实际生产后台 runner 才能继续 Dispose 和调用目录 action。`close-window-external-observation.json` 在外部 shell 中记录两者存活；相关事件先 main-closed，再 process-disposed、folder-adapter。

第二次使用全新进程且不创建 keeper，最后窗口关闭使 WinUI 宿主退出；`last-window-external-observation.json` 由外部 shell 保存 child 存活状态。记录中的 **hostExitCode=null**：该次没有提前保留宿主 handle，因此只证明已退出，不声称宿主退出码 0；子进程则提前持有外部 handle，真实 ExitCode=0 断言通过，并有 child-exit.json 相互印证。生产 async continuation 没有在死掉的宿主中执行，日志没有 Dispose/folder callback，不能称为完成回调通过。OS 进程回收也不能冒充托管 using 已执行。

静态阅读真实 `MainWindow.OnClosed`：有播放器时设置 Handled 并 HideAllWindows；没有播放器时关闭其余窗口、保存服务/窗口状态后调用 App.Exit / Environment.Exit(0)。本次没有链接该生产 MainWindow、播放器/托盘、App 单实例/激活和账号导航组合，也没有改变它们来制造通过。因此两种 harness 关闭实验支持 **生产下载代码不主动杀 child** 的有限实机结论，不能签收生产整套关闭/隐藏/退出行为。该完整无账号入口无法在不组合生产账号/媒体服务的当前夹具中隔离，列为未验。
